Evaluation
(a) Strategy for availability rules / room filters — not warranted. checkAvailability already composes four small pure functions (validateInterval, checkDuration, blocked check, overlapsExisting). A Strategy would let callers swap rule implementations at runtime, but no caller ever swaps them and the rule set is fixed. It would add polymorphism and indirection that solve none of the reported pain. The current composition is the right shape; the duplication is in parsing, not in rule selection. Reject.
(b) Adapter for raw form values — the instinct is right, the ceremony is not. The real defect is three parsers (timeToMinutes, parseInt, Number) scattered across App and two components for what are ultimately three numeric fields. An Adapter that yields one typed request object ({ startMin, endMin, currentTime }) would centralize this, but naming it "Adapter" and giving it a class/interface is overweight: a single pure function does the same job with no indirection.
Recommendation
Add one pure function — e.g. parseBookingRequest(startTimeStr, endTimeStr, currentTimeStr) returning { startMin, endMin, currentTime } — that keeps each field's original parser verbatim (timeToMinutes for start, parseInt(…,10) for end, Number for current/attendees). Call it once in App; pass the result to checkAvailability and BookingForm. This removes the scattered-conversion smell, gives a single place to audit parsing, and changes no behaviour. No Strategy, no Adapter class — one function.
What could go wrong
- parseInt vs Number divergence. parseInt('') is NaN but Number('') is 0; parseInt('12abc') is 12 but Number('12abc') is NaN. If the "unification" silently swaps end's parseInt for Number, empty/partial input flips from "invalid interval" (caught by isNaN) to 0, which then trips start >= end or end > 1440 with a different reason text. Since reason texts must not change, preserve each parser exactly.
- currentTime/attendees parsing lives in component onChange, not App. Moving it out means the components emit raw strings and App owns all conversion — a slightly larger diff. If you leave their Number() in place and only centralize start/end, you get most of the benefit with a smaller change but the four-call-site count drops to three, not one.
- attendees is already numeric in state and flows to filterRooms unchanged; folding it into the same function risks coupling room-filter parsing to booking parsing for no domain reason. Keep them separate.
Net: one small pure function, original parsers preserved, behaviour identical. No pattern required.
